Here's the full plan. First, the thing to unblock everything else: there is no fix here that is a matter of installing something or changing a setting. Persian on this panel is a code change, and it's three separate pieces of work — glyph data, letter shaping, and text reordering. They have to all be there or you get boxes again.

## The decision that shapes the scope

Before any code: which strings become Persian? This matters more than it sounds, because most of the text this device shows is not a fixed label — it's English prose generated by `describe()` functions with f-strings baked in:

- `limits_guard.describe()` at `src/limits_guard.py:471` emits lines like `boiler 1: ok; setpoint 70.0 °C; probes boiler_body; cut 73.0 °C, restore 68.0 °C`
- `device_config.describe()` at `src/device_config.py:302`
- `device_record.describe()` at `src/device_record.py:522`
- `schedule_runner.describe()` at `src/schedule_runner.py:757`

Those are the hardest part and also the ones an operator most needs to read correctly. A mistranslated cut-out threshold is a safety problem, not a cosmetic one.

So there are two scopes, and I'd do them in this order:

**Scope 1 — fixed labels only.** The ~9 items in `MAIN_ITEMS` (`control_menu.py:135`), the submenus, and the panel titles. Maybe 30 short strings total. These are translatable by hand.

**Scope 2 — the generated `describe()` output.** Every formatted line.

Do Scope 1 first, get it on the panel, look at it in the boiler room at night under whatever light is actually there. That tells you whether 5×7 is legible enough to justify Scope 2 at all. Trying to do both at once and discovering the glyphs are too small means throwing away the translation work too.

## Step 1 — build the glyph table offline, on your laptop

The device should not get a font library. Here's why that's the right call for this codebase specifically: `requirements.txt` is currently two packages (`websockets`, `tzdata`) and the hardware add is two more. Every dependency here earns its place, blocking I/O goes through `asyncio.to_thread`, and you're targeting a Pi Zero W on a single ARMv6 core. Adding Pillow at runtime would be the first heavy thing in the tree.

Instead, rasterize once on a development machine and commit the result.

On your laptop:

1. `pip install Pillow` and get a Persian font. Vazirmatn is the usual choice — it's designed for exactly this, readable at small sizes. Noto Naskh Arabic is a more traditional fallback.
2. Render each codepoint you need at the size matching the cell. For the existing 5×7 glyph in a 6×8 cell, render at 7px tall and threshold to 1-bit.
3. Pack each glyph into the same column-byte format `_FONT` already uses. The format is five bytes, one per column, bit 0 = top row. So for each glyph, for x in 0..4, build a byte where bit `y` is set if pixel (x, y) is on.
4. Emit a Python module — `display_font_fa.py` — with two dicts: one for the base codepoints, one for the Arabic Presentation Forms-B range (`U+FE70`–`U+FEFC`), which is where the shaped letterforms live.
5. Commit it. It is data, generated once, checked in like the existing `_FONT`.

That last point matters: the new module is a build artifact but it lives in the repo permanently, because the device has to run without the toolchain. Same relationship the font module has to the font choice.

## Step 2 — write the joining logic

This is the part that has to be right, and it's the part that a lookup table alone can't do.

Persian is a cursive script. A letter's shape depends on what surrounds it. The same codepoint has up to four forms:

- **isolated** — nothing joins to it
- **initial** — joins only to the next letter
- **medial** — joins to both
- **final** — joins only to the previous letter

Each Persian letter has one of three joining behaviours, and that's the whole classification:

| Behaviour | Letters | Forms it can take |
|---|---|---|
| Dual-joining | ب پ ت ث ج چ ح خ س ش ص ض ط ظ ع غ ف ق ک گ ل م ن و ه ی | all four |
| Right-joining | ا آ د ذ ر ز ژ و ة ۀ ئ | isolated, final |
| Non-joining | ء ؤ, space, punctuation, digits | isolated only |

Build a table mapping `(letter, prev_joins, next_joins)` to the Presentation Forms-B codepoint. Persian has roughly 32 letters × 4 forms, so about 100 entries, and the table has legitimate holes — a non-joining letter simply has no initial or medial form, and you fall through to the base codepoint.

The algorithm itself is a single pass over the string:

1. Classify every character as dual / right / non-joining / transparent.
2. Transparent means diacritics — the fatha, kasra, sukun, shadda and their Persian equivalents in the combining range. They take no shape of their own and must not break a join.
3. For each base letter, look left and right, skipping transparents, and ask: does the previous neighbour join forward, and does the next one join back?
4. Emit the matching form.

Put this in a new `src/text_shaper.py` as a pure function, `shape(text) -> str`, with no dependency on the canvas or the hardware. Pure function, no I/O, easily testable on a laptop against a handful of words you can check by eye.

This is where the alternative deserves naming: the `arabic_reshaper` and `python-bidi` packages do this for you, and do it well. But they add two runtime dependencies and carry configuration defaults that surprise people, and the shaping rules for Persian specifically are about 100 lines. On this codebase, hand-rolled is the better trade. If you disagree, this is the one step where swapping in the package is a clean substitution.

## Step 3 — handle the right-to-left reordering

Shaping gives you correct letterforms in source order. It does not give you the right order on screen. `"بخار"` is shaped correctly but the canvas draws left to right, so you also need the run reordering.

The good news: Python's standard library has this. `unicodedata.bidirectional()` returns the bidi class of any character — `AL` for Arabic letter, `AN` for Arabic-Indic digit, `EN` for a European digit, `R`, `WS` for whitespace, and so on. That gives you everything needed to reverse by runs without any dependency.

The rule is: reverse the *order of runs*, not the characters inside them. A Persian run reverses. A number does not — `"68"` must render as 68, not 86, and that's the case that will bite you, because this UI is full of temperatures and thresholds. The standard approach is a small simplified bidi: identify runs of strong RTL versus everything else, reverse the RTL runs, and leave LTR runs and numbers intact. You do not need full UBA conformance for a menu.

I already checked one thing in your favour: `Screen.frame()` at `src/screen.py:132` does `title.upper()`. On Persian that's a no-op — the script has no case — so titles pass through unharmed.

## Step 4 — wire it into the canvas

Small change, in one place. At the top of `Canvas.text()` (`src/display_canvas.py:130`), before the character loop, check whether the string contains anything above U+0700. If it does, run it through shape-then-reorder. If it doesn't, take the existing path untouched.

That conditional matters: the overwhelmingly common case is ASCII, and you don't want a Python function call per keypress redraw for every English label.

`Canvas.text()` then draws codepoints in the order it receives them, which is the wrong one for Persian. Reordering in step 3 is what makes the existing left-to-right loop correct.

One thing you don't need to do: mirror the glyphs for the selection highlight. In `Screen.select()` the selected row is drawn with `on=False`, which inverts the bitmap. Inverse Persian is still correct Persian. `Canvas._span()` at `display_canvas.py:65` handles this properly with `^=` in invert mode.

## Step 5 — deal with the width

This is the constraint that will decide whether Scope 2 is worth doing, so find out early rather than late.

At 5×7 in a 6×8 cell you get 21 columns across and 8 rows down. `screen.py:62` computes `BODY_COLUMNS = 20` and `BODY_ROWS = 6` between the title bar and legend strip. Persian is compact — a word like `خوانش` is 5 characters against 9 for "readings" — but the `describe()` lines are already long and already depend on `wrap()` to fold them.

`wrap()` at `display_canvas.py:203` will work as-is: it breaks on spaces, and Persian uses spaces between words. That part is fine.

Two things need attention:

- `truncate()` at `display_canvas.py:186` cuts at `columns - 1` and appends `~`. That's fine on a shaped string, because shaping already happened and cutting mid-word just drops characters.
- `Screen.read_line()` at `src/screen.py:370` shows `text[-(BODY_COLUMNS - 2):]` — the tail of what you've typed. For a right-to-left string, the tail is on the left. This needs to become "the visually last characters" once Persian input exists. Low priority, since no prompt should ever ask you to type Persian.

If 5×7 turns out illegible, the fix is a bigger cell, and you should know before starting that it is not a font-table change. `CELL_WIDTH` and `CELL_HEIGHT` at `display_font.py:22` are load-bearing for `COLUMNS`/`ROWS` in `display_canvas.py:26`, for `BODY_COLUMNS`/`BAR_COLUMNS` in `screen.py:62`, and for the legend width arithmetic (`_SCROLL_WIDTH` at `screen.py:72`, `_entry_width`, the gap-fitting loop in `_legend`). Going to 8×10 gives you 16 columns and would require reworking all of it plus rewriting every label to fit. That is why Step 6 matters.

## Step 6 — verify on the panel before you translate anything

You can do this without hardware, which is the good news.

`MockDisplay` at `src/mock_display.py:63` renders the exact frames the ST7920 would receive, as half-block text in a terminal. `Canvas` is pure bytes with no hardware import at all. So:

1. Write the shaping and glyph work.
2. Run with `BOILERROOM_DISPLAY=mock` and the mock keypad.
3. Turn on `BOILERROOM_KEYPAD_EMULATE=on` so the screens are driven by the real key table.
4. Look at the frames in a terminal at the size the terminal renders them.

What that catches: wrong letterforms, missing joining, reversed numbers, and overflow past 20 columns.

What it does not catch: whether it's legible in the boiler room. For that you need the real panel, in place, at the real viewing distance, in the light it actually has. The `MockDisplay` half-block output is roughly the right pixel count and completely wrong contrast.

`display.py:897` already has a bring-up mode — `python src/display.py --test` — that draws a diagnostic frame. Extend that to draw your Persian sample strings so you have a repeatable test card rather than a one-off.

## Step 7 — translate, and keep the parsers numeric

When you do translate the `describe()` output, keep every input prompt numeric. This is already the case and it's deliberate: `parse_days()` at `schedule_editor.py:96` accepts `135` for Monday/Wednesday/Friday, `parse_time_text()` at `schedule_editor.py:141` accepts `0730`, `parse_date_text()` at `schedule_editor.py:174` accepts `0` for today and `1` for tomorrow. That exists because the keypad is sixteen keys with no letters — `keypad_layout.py:135`. A Persian keypad would change nothing about that, and you should not let the translation tempt you into adding a text field. Labels become Persian; the digits stay digits.

Also worth preserving: `mock_keypad.py:128` refuses an answer containing a character the real keypad cannot produce, and reports it as a prompt you cannot answer from the device. Any translation that makes a prompt unanswerable on the hardware will show up there first, on your laptop, before it reaches the panel.

## What this costs in summary

| Piece | Work | Runtime deps |
|---|---|---|
| Glyph table | Generate from a TTF once, commit | none (Pillow is build-time only) |
| Shaping | ~100-line table + single pass, `text_shaper.py` | none, or `arabic_reshaper` |
| Reordering | Simplified bidi over `unicodedata.bidirectional()` | none |
| Canvas hook | Conditional in `Canvas.text()` | none |
| Layout, if 5×7 is too small | Rework cell size across `display_canvas.py` and `screen.py` | none |
| Translation | Scope 1, then Scope 2 | none |

Zero new runtime dependencies, which keeps this consistent with how the rest of the agent is built.

The natural first switch is: Steps 1 through 4, plus Step 6's mock-display test card, with no translation yet. That gets you a Persian sample string rendering correctly on the panel, which is the only way to find out whether the cell size is a real problem before you spend effort on 30 strings and a format string.
